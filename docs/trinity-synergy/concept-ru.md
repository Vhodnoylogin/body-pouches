# Взаимодействие HIGGS VRIK PLANCK PPB и Body Slots

English: [English version](concept-en.md).

Это предложение общей архитектуры для HIGGS, VRIK, PLANCK, PPB, Body Slots и модов, построенных на них. HIGGS управляет всеми состояниями и способами использования рук, Body Slots — всей механикой слотов, VRIK — телом и положением виртуальных рук, PLANCK — физикой NPC, PPB — анатомическими поверхностями, их подгонкой и данными касаний. Каждый предоставляет остальным необходимые данные и запросы. Полный API пока не реализован и не согласован с авторами; [документ выполненной работы](implementation-status.md) отделяет реализацию от примеров интерфейсов. Обновление концепции от 31 октября 2026 года не возобновляет разработку.

Цель — позволить мододелу запросить зону на теле, передачу предмета или взаимодействие с NPC через понятный контракт. У каждого действия должны быть определены владелец, условия выполнения и подтверждённый результат.

## Ответственность участников

| Участник | Ответственность | Что получает сторонний мод |
|---|---|---|
| HIGGS | Единая модель всех состояний рук, все способы их использования, ввод grip/trigger, резервирование, очередь вибрации и физическое удержание | Закрытые состояния занятости и доступности, разрешения на действия, общие операции захвата предмета и опоры, поддержки оружия, отпускания, передачи и потребления, подтверждённые результаты |
| VRIK | Тело игрока, калибровка и положение виртуальных рук | Согласованные наблюдения позы кистей и опорных узлов тела с координатами, временем, актуальностью и поколениями |
| PLANCK | Физическая анимация NPC, жизненный цикл ragdoll, распознавание и подтверждение его физических попаданий | Данные актора, костей и физических тел; допустимые точки прикрепления; события попаданий и изменения физического состояния; временные политики взаимодействия |
| PPB | Определения анатомических поверхностей, подгонка к форме тела и смысл данных касания | Покрытие поддерживаемых тел, фактическая геометрия капсул, анатомические области, квалифицированные наблюдения контактов; предложения геометрии применяет владелец физического тела |
| Body Slots (рабочее название) | Вся механика слотов: определения и экземпляры, привязки, геометрия, обнаружение, активация, отображение, правила содержимого и сохранение подгонки | API создания и настройки, пакеты определений, слоты экипировки, события зон, предложения действий, адресованные запросы обработчикам и наблюдаемые результаты |
| Сторонний мод | Собственная игровая механика и правила содержимого | Возможность реализовать сумку, нестандартную экипировку, жест отпускания, вес оружия, проникновение клинка или парирование через общие контракты |
| CommonLib | Работа с адресами и типами движка, общие технические операции и проверенные обёртки | Единая реализация доступа к движку, геометрии, сцене и физике для участников синергии и сторонних модов |

HIGGS предоставляет единый ввод, модель руки и контроль всех способов её использования. Провайдеры могут распознавать игровые жесты и предлагать действия, но используют закрытый набор общих операций HIGGS. Body Slots распознаёт взаимодействие со своими слотами; VRIK поставляет позу, не выбирая действие слота. Собственный распознаватель не даёт права создать второй физический привод или обойти выбор HIGGS.

HIGGS может передавать результат операции другого мода, сохраняя его владельца. Это не переносит в HIGGS правила содержимого сумки или расчёт каждого вида урона.

## HIGGS ввод удержание и физические запросы

HIGGS — единственный владелец общей модели состояний рук и согласования всех способов их использования. Он получает наблюдения игровой экипировки от движка и положения виртуальных кистей от VRIK, управляет физическими руками, вводом, хватами, резервированием и вибрацией. Body Slots и другие потребители получают состояние и права от HIGGS без собственного параллельного классификатора. Перемещение персонажа, правила сбора, содержимое слотов и расчёт урона остаются у владельцев игровых механик; HIGGS направляет разрешённые операции назначенному исполнителю и сообщает результат.

### Ввод и выбор действия

Распознаватели используют один поток ввода и предлагают действия до выполнения действия по умолчанию. InputBinding описывает контекст, действие, срок распознавания и поведение отложенного ввода. ActionCandidate указывает последовательность ввода, необходимые ресурсы и зарегистрированного исполнителя. HIGGS выбирает допустимое действие по пользовательскому приоритету и сообщает решение. Body Slots предоставляет пространственный контекст слота; другие распознаватели тоже работают через этот механизм.

**Псевдо-ABI — пример, не окончательный интерфейс.**

```cpp
namespace HIGGS {

Status CopyInput(ClientToken, PhysicalHand, InputObservation* outInput);

Status RegisterRecognizer(ClientToken, const InputBinding*, RecognizerCallback, void* userContext, Lease* outRegistration);

Status SubmitActionCandidate(ClientToken, const ActionCandidate*, RequestId* outRequest);

// Events: InputChanged.

}
```

Механизм выбора предоставляет действующий приоритет и основание решения. Сторонний мод может прочитать их, не получая права повторно использовать то же нажатие для другого действия. Запросы вибрации попадают в общую согласованную очередь.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status CopyEffectiveInputPriority(ClientToken, const InputContext*, InputPriority*);

Status CopyInputDecision(ClientToken, uint64_t sequenceId, InputDecision*);

Status RequestHaptic(ClientToken, const HapticRequest*, RequestId* outRequest);

// Events: InputDecisionMade.

}
```

### Состояние руки и согласованные наблюдения

HIGGS предоставляет закрытую модель из двух независимых характеристик. Моды не регистрируют новые значения состояний:

| Занятость | Значение |
|---|---|
| Empty | Подтверждено отсутствие и удержания HIGGS, и игрового предмета в руке |
| GameEquipped | Предмет используется в руке через игровую экипировку |
| HiggsHeld | Объект физически удерживается HIGGS |
| Both | Подтверждены оба вида занятости |

| Доступность | Значение |
|---|---|
| Ready | Нет известного запрета на новое взаимодействие; конкретное действие проверяется отдельно |
| Reserved | Использование руки закреплено за согласованной операцией; переход требует её правил освобождения или передачи |
| Unavailable | Известна причина недоступности руки |
| Unknown | Данных недостаточно или они противоречат друг другу |

Предмет, только выбранный в инвентаре, ещё не доказывает занятость руки: HIGGS учитывает фактическое использование и состояние оружия. Запись указывает, какие сведения о занятости установлены; если установить их нельзя, значение не выдаётся за Empty, а доступность остаётся Unknown. Известные предметы можно сохранить в наблюдении и при неопределённой доступности. Нулевой указатель сам по себе не доказывает свободную руку.

Лазание и поддержка оружия не становятся новыми состояниями. HIGGS выражает их через общие операции и владение ресурсом; имя владельца помогает диагностике, но не расширяет список состояний. Unknown не обнаруживает скрытое состояние произвольного мода: участники синергии обязаны пользоваться общими операциями, для старых модов применяются подтверждённые наблюдения и адаптеры. Отсутствие сведений не даёт гарантии совместимости.

**Псевдо-ABI**

```cpp
namespace HIGGS {

enum class HandOccupancy : uint32_t { Empty, GameEquipped, HiggsHeld, Both };

enum class HandAvailability : uint32_t { Ready, Reserved, Unavailable, Unknown };

}
```

CopyHandState различает физические левую и правую руки и ведущую или вторую руку. Событие ввода или отпускания указывает соответствующий отсчёт позы: Body Slots проверяет свою геометрию по согласованному наблюдению, не соединяя раннее отпускание с произвольной текущей позой. Сам по себе колбэк после обновления такой гарантии не даёт. Повторный захват, употребление, загрузка или потеря отслеживания отменяют ожидающие предложения до их выполнения.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status CopyHandState(ClientToken, PhysicalHand, HandState* outState);

Status CopyReleaseObservation(ClientToken, uint64_t releaseId, ReleaseObservation* outRelease);

// Events: InteractionChanged.

}
```

Выборки движения различают движение контроллера в пространстве отслеживания и предмета в мире, указывая версию преобразования между ними. Перемещение персонажа, телепорт и перекалибровка могут изменить её без смены мира и тела. Данные контакта содержат источник, объект, точку, нормаль, движение и поколения тел; контакт с растением или стеной отделён от попадания по NPC.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status CopyMotionSamples(ClientToken, PhysicalHand, PoseSource, uint32_t space, MotionSample* outSamples, uint32_t capacity, uint32_t* outCount);

Status CopyContactSnapshot(ClientToken, const ContactQuery*, ContactSnapshot*);

// Events: ContactChanged.

}
```

### Общие способы использования рук

Перечень общих операций фиксируется версией ABI HIGGS: захват предмета, отпускание, передача предмета, поддержка оружия второй рукой, захват опоры мира, использование игровой экипировки, потребление и согласованная цель позы руки. Игровые сценарии составляются из этих операций. Новому моду не разрешается зарегистрировать произвольный новый вид физического управления: новый общий примитив требует явного расширения версии и возможностей HIGGS. Параметры привода, ограничения и отключение возможностей настраивают поддержанные операции, а не создают второй механизм хвата.

Мод лазания запрашивает у HIGGS стандартный захват опоры и после подтверждения управляет перемещением игрока. Физическую опору, владение рукой и освобождение обслуживает HIGGS. Операции с несколькими руками согласуются совместно. Для игровой экипировки исполнитель может оставаться у движка или профильного мода, но общая модель руки и разрешение операции принадлежат HIGGS.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status RequestHandUse(ClientToken, const HandUseRequest*, Lease* outUse, RequestId* outRequest);

Status RequestEndHandUse(ClientToken, Lease use, RequestId* outRequest);

// HandUseRequest names a supported operation kind; no custom physical driver.
// Events: HandUseChanged.

}
```

### Захват отпускание и передача

Запросы захвата, отпускания и передачи указывают руку и сообщают фактический результат. Передача из инвентаря в руку отдельно подтверждает изменение инвентаря и физический захват, включая ссылку предмета, количество и конечное положение. Она резервирует источник, назначение и удержание, сохраняет данные экземпляра и изменяет инвентарь одним уполномоченным исполнителем ровно один раз. Если после извлечения захват не удался, назначенный исполнитель выполняет предусмотренную компенсацию. Повтор запроса или обновление изображения не создают новый предмет; произвольные побочные действия скриптов не позволяют гарантировать полный откат.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status RequestGrab(ClientToken, const GrabRequest*, RequestId* outRequest);

Status RequestRelease(ClientToken, const ReleaseRequest*, RequestId* outRequest);

Status RequestTransfer(ClientToken, const TransferRequest*, RequestId* outRequest);

// Events: ActionResult.

}
```

### Физические ограничения

Изменения хвата, привода и ограничений применяются в разрешённой фазе и имеют подтверждение. Временные воздействия указывают владельца, руку или предмет и срок действия. Отключение выбранных возможностей не отпускает предмет: отпускание задаётся отдельным запросом. Завершение лазания снимает только воздействия его владельца, сохраняя ограничения другого мода.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status RequestGripChange(ClientToken, const GripChange*, RequestId* outRequest);

Status RequestHandGoal(ClientToken, const HandGoal*, Lease* outGoal, RequestId* outRequest);

Status RequestDrivePolicy(ClientToken, const DrivePolicy*, Lease* outPolicy, RequestId* outRequest);

Status RequestHandGeometry(ClientToken, const HandGeometryRequest*, RequestId* outRequest);

Status RequestConstraint(ClientToken, const ConstraintRequest*, Lease* outConstraint, RequestId* outRequest);

Status RequestSuppression(ClientToken, const SuppressionRequest*, Lease* outLease, RequestId* outRequest);

// Events: ConstraintChanged.

}
```

### Исполнители действий

Сторонний мод регистрирует путь выполнения; распознавание и проверка доступности не изменяют инвентарь. Результат принимается только от назначенного исполнителя при совпадении провайдера и поколения запроса. Повторное подтверждение игнорируется, зафиксированная стадия не возвращается назад. HIGGS передаёт результат, сохраняя полномочия исполнителя над операцией.

**Псевдо-ABI**

```cpp
namespace HIGGS {

Status RegisterActionExecutor(ClientToken, const ActionExecutorInfo*, ActionExecutorCallback, void* userContext, ExecutorId* outExecutor, Lease* outRegistration);

Status ReportExecutionResult(ClientToken, const ExecutionResult*);

}
```

## VRIK тело и положение рук

### Тело и положение рук

VRIK отвечает за виртуальное тело, калибровку и положение виртуальных рук. **IK (inverse kinematics) — обратная кинематика:** по голове и кистям рассчитывается поза остальных костей, включая плечи и локти. HIGGS управляет физическим использованием рук и предоставляет разрешённые цели хвата; VRIK согласует с ними видимую позу. Зоны, слоты, их содержимое, активация и отображение относятся к Body Slots. Перемещение персонажа остаётся у владельца механики.

Контроллер, физическая ладонь или точка хвата HIGGS и виртуальная кисть VRIK — разные наблюдения с временем, доступностью, координатами и поколением. VRIK предоставляет положение кисти и опорных узлов тела; HIGGS определяет состояние и доступность руки, а Body Slots проверяет попадание выбранной точки в свою геометрию. Цель использования руки запрашивается через HIGGS; VRIK остаётся единственным владельцем расчёта позы скелета. Итог IK не становится целью физического привода в том же цикле.

**Псевдо-ABI**

```cpp
namespace VRIK {

Status CopyHandPose(ClientToken, PhysicalHand, HandPose* outPose);

Status CopyBodyAnchor(ClientToken, const BodyAnchorQuery*, BodyAnchorSnapshot* outAnchor);

// Events: PoseAvailable, BodyAnchorInvalidated.

}
```

Это предлагаемый контракт наблюдений, а не утверждение о наличии этих методов в выпущенном VRIK. Изученный публичный интерфейс 001 не содержит общего GetHandPose. Независимый адаптер Body Slots может читать доступные игровые узлы, которые обновляет VRIK, с проверкой фазы, координат, калибровки и актуальности; при недостатке данных он сообщает недоступность. Новые слоты проектируются без обязательной правки VRIK и без использования реконструированного кода. При этом проверенная совместимость адаптера с конкретной версией VRIK остаётся отдельной задачей.

## PLANCK физика NPC и попадания

### Тела акторов и точки прикрепления

PLANCK отвечает за физическую анимацию NPC, переходы к ragdoll и обратно, актуальность физических тел. Он предоставляет данные актора, костей и тел, подтверждённые точки прикрепления. PPB предоставляет анатомическую геометрию поверхностей и предложения по подгонке; PLANCK сохраняет владение применением изменений и жизненным циклом физических тел NPC, проверяя предложения без создания конкурирующего ragdoll. Мод проникновения управляет раной и извлечением; PLANCK проверяет тело цели, HIGGS применяет ограничение оружия.

```cpp
namespace PLANCK {

Status CopyActorPhysics(ClientToken, ActorHandle, ActorPhysics* outState);

Status AcquireAttachmentEndpoint(ClientToken, const AttachmentQuery*, AttachmentEndpoint* outEndpoint, Lease* outEndpointLease);

// Events: ActorPhysicsChanged, EndpointInvalidated.

}
```

Точки прикрепления указывают поколения мира, актора и тела. Замена ragdoll, выгрузка NPC или загрузка игры безопасно отменяют зависимые точки и ограничения. Политика актора действует в заявленной области, не меняя пороги для всего оружия. Растениям и скриптовым активаторам PLANCK нужен лишь при фактическом взаимодействии их механики с его акторами.

**Псевдо-ABI**

```cpp
// Events: ActionResult.
```

```cpp
}
```

## PPB поверхности тела и касания

Precision Physic Bodies (PPB) предоставляет слой анатомической геометрии: какие поверхности есть у тела, как его капсулы подогнаны к реальной модели и какой части тела касается рука или предмет. VRIK создаёт позу тела игрока; PPB описывает поверхности; HIGGS управляет использованием рук; PLANCK — физической анимацией NPC и жизненным циклом их физических тел. Касание предплечья — данные для выбора действия, а не разрешение схватить, экипировать или нанести урон.

### Геометрия поверхностей и подгонка

PPB отвечает за определения анатомических форм, подгонку под поддерживаемые модели и скелеты, классификацию областей тела. Предлагаемый контракт наблюдения указывает актора, поверхность, сторону и дочернюю капсулу, фактическую геометрию в мировых координатах, единицы, фазу и время выборки, актуальность и поколения модели, тела и формы. Ключ поверхности связан с провайдером и поколениями; голый индекс капсулы не является постоянным идентификатором для сохранения. Контракт также сообщает покрытие: неподдерживаемое тело недоступно, а не «не имеет касаний».

**Псевдо-ABI**

```cpp
namespace PPB {

Status CopySurfaceSnapshot(ClientToken, const SurfaceQuery*, SurfaceSnapshot* outSurfaces, uint32_t capacity, uint32_t* outCount);

Status CopyCoverage(ClientToken, ActorHandle, SurfaceCoverage* outCoverage);

Status CopyShapeProposal(ClientToken, const ShapeFitQuery*, ShapeProposal* outProposal);

// Events: SurfacesChanged, SurfacesInvalidated.

}
```

PPB вычисляет предлагаемые изменения формы как данные. В целевой архитектуре PLANCK проверяет и применяет физическую геометрию NPC в разрешённой фазе изменения; HIGGS делает то же для физических тел кистей и пальцев. Запросы указывают ожидаемые поколения модели и тела, версию геометрии; владелец физического тела сообщает, применено ли изменение и когда. У каждого физического тела один владелец публикации и жизненного цикла. PPB может подгонять форму и читать применённый результат без второго привода руки, независимой замены того же тела или изменения глобальных настроек другого провайдера. Это предлагаемая граница интеграции: нынешний PPB также сам создаёт коллайдеры рук и встраивается в цепочки физических обновлений.

### Данные касания и право на действие

PPB сообщает анатомическую цель и данные касания; HIGGS — достоверное состояние руки и связанную с ней идентичность руки или предмета. Классификация источника касания описывает наблюдение, а не создаёт ещё одну расширяемую машину состояний рук. Предлагаемая запись контакта различает близость, геометрическое пересечение и подтверждённый движком контакт, указывает пробу и фазу выборки, явно отмечает недоступные точку, нормаль и импульс. Геометрическая глубина пересечения сама по себе не доказывает физическую силу.

**Псевдо-ABI**

```cpp
namespace PPB {

Status CopyTouchSnapshot(ClientToken, const TouchQuery*, TouchSnapshot* outContacts, uint32_t capacity, uint32_t* outCount);

Status SubscribeTouches(ClientToken, const TouchSubscription*, TouchCallback, void* userContext, Lease* outSubscription);

// Events: TouchBegan, TouchChanged, TouchEnded, TouchStreamReset.

}
```

Касание может сделать игровое действие доступным. HIGGS выбирает между конфликтующими действиями рук; PLANCK распознаёт и подтверждает свои физические попадания. PPB добавляет анатомические подробности к соответствующему наблюдению, не создавая второго попадания. Существующие функции толчков и экипировки PPB могут остаться игровыми провайдерами: они сохраняют пороги реакции и правила одежды, запрашивая операции рук у HIGGS, политики и реакции NPC у PLANCK, изменения экипировки — у назначенного исполнителя. Наблюдение касания не даёт всем подписчикам самостоятельного права выполнить действие.

### Существующий API и предлагаемое расширение

В [открытых исходниках](https://github.com/Telord72612/Precision-Physic-Bodies) уже есть [IPpbTouchInterface1](https://github.com/Telord72612/Precision-Physic-Bodies/blob/e26b4ebc8061e8736b344e4f3e9216dea9254747/src/PpbTouchAPI.h#L446), получаемый через сообщения SKSE. Он предоставляет запросы покрытия, фактические концы и радиус капсулы в мировых игровых единицах, анатомические названия и сгруппированные наблюдения касаний digest/raw. Нативные методы вызываются только из главного потока. Это полезная основа интеграции, которую не надо изобретать заново.

Существующее поле `slot` в PPB обозначает анатомическую группу тела, а не слот взаимодействия Body Slots. Нынешние запросы эталонных названий не являются универсальным каталогом поверхностей конкретного актора; потребитель проверяет покрытие и реально читаемую геометрию его тела.

[Текущий контракт касаний](https://github.com/Telord72612/Precision-Physic-Bodies/blob/e26b4ebc8061e8736b344e4f3e9216dea9254747/INTEGRATION.md#L545) описывает касания игроком NPC с поддерживаемыми телами. Он не обещает полную геометрию тела игрока как цели, касания NPC друг друга, регистрацию произвольных поверхностей или согласованную передачу владения физическими телами. Отчёты digest и raw сгруппированы и отфильтрованы по длительности; ни один не является полным мгновенным набором пересечений каждой капсулы. Глубина digest обобщает посещение области, а частота колбэков определяется настройкой отчётности. Новый контракт оперативных наблюдений и жизненного цикла не должен незаметно подменять эту семантику. Согласованные поколения, удаление подписки и сброс потока, идентичность поверхностей конкретного актора и согласованное применение физических форм — кандидаты на расширение, а не готовые службы.

У PPB своя роль в синергии, но мод требует его только тогда, когда использует его анатомию или данные касаний. Body Slots сохраняет собственные области доступа и не требует касания кожи: отверстие сумки может находиться перед телом. Необязательная анатомическая привязка или подгонка к телу может использовать PPB только при подтверждённом покрытии; поддержку тела игрока нужно отдельно добавить и проверить. Потеря PPB делает недоступными зависимые наблюдения, а не остальные слоты, привязанные к узлам. Morphbench может редактировать и сопоставлять капсулы рядом с размещением слотов, не становясь владельцем геометрии или взаимодействий в игре.

## Body Slots вся механика слотов

Слот — именованная настраиваемая область на теле или возле тела игрока с подключённым поведением взаимодействия. Вход руки меняет пространственный контекст; согласованное нажатие может вызвать предложенное действие. Область, видимая сумка и контейнер инвентаря — разные сущности: одна сумка может добавлять несколько слотов, а слот не обязан иметь собственный запас предметов.

**Body Slots** предоставляет расширяемую систему слотов без архитектурного ограничения четырнадцатью кобурами VRIK и оружейными типами. Он владеет всей механикой слотов: созданием, привязкой к телу и экипировке, геометрией, входом и выходом руки, наведением, предложениями действий, активацией, отображением и сохранённой подгонкой. VRIK предоставляет тело и положение виртуальных рук; HIGGS предоставляет их состояние и согласует все способы использования. Тип содержимого и игровая реакция определяются настройками и провайдерами слота. Само действие выполняется через общие операции соответствующих служб. Практические пределы ресурсов явно задаются реализацией. Редактор вне игры и API создания — два способа предоставлять слоты; само редактирование вне игры не является смыслом службы.

Штатные четырнадцать кобур VRIK сохраняются как существующая система. Новые слоты Body Slots не требуют их замены. В полном режиме перехода штатные кобуры отключаются и заменяются четырнадцатью аналогами Body Slots с теми же принимаемыми типами и положением, дополненными слотами модов. Сопоставление настроек и назначений проверяется отдельно; для каждого эквивалентного слота активен один путь взаимодействия и отображения. Сосуществование требует явно согласовать конкурирующие кобуры доступными средствами, а не считать, что HIGGS автоматически контролирует неизменённый VRIK. Полный переход остаётся целевым режимом совместимости, не условием создания новых слотов и не готовой возможностью прототипа.

### Визуальный редактор до запуска игры

Основной путь: **визуальный редактор вне игры → редактируемый проект и пакет слотов с версией → Body Slots: привязка, проверка зон, взаимодействие и отображение; данные тела и положения рук от VRIK, состояние рук и согласование ввода от HIGGS**. Редактор загружает эталонное тело, скелет или модель экипировки. Автор выбирает именованную точку крепления, размещает и поворачивает слот, редактирует независимую область доступа, задаёт правила масштаба, доступ для физических рук, вид слота, допустимое содержимое и при необходимости визуал. У надеваемой сумки для зелий область доступа можно расположить у отверстия ещё до запуска Skyrim.

Редактируемый проект сохраняет данные для дальнейшей работы автора; экспорт представляет собой декларативный пакет с версией, который мод слотов проверяет и загружает. Для создания, повторного открытия и экспорта определений не нужны ни Skyrim, ни VRIK. Мод может поставлять такой пакет без вызовов API во время игры. Формат указывает постоянные ключи провайдера и слота, версии схемы и эталонного скелета, имена точек крепления, локальные преобразования, геометрию и проверяемые точки, единицы, оси, правила масштаба, привязки политик и ссылки на ресурсы. Указатели движка и временные идентификаторы сохранения в пакет не попадают; игровые колбэки доступности в редакторе не выполняются.

Инструментом для подготовки слотов выбран [Morphbench](https://github.com/Vhodnoylogin/morphbench): отдельный режим Slots использует его существующий просмотр моделей и скелета. Этот режим редактирует размещение относительно узлов и экспортирует определения Body Slots; он не становится ещё одним менеджером слотов в игре. Привязки к узлам скелета и физические тела остаются разными сущностями. Отсутствующий узел нельзя показывать как действующую привязку с выдуманным преобразованием. Реализованные функции и оставшиеся требования к редактору отмечены в [документе о ходе реализации](implementation-status.md).

Размещение вне игры задаёт исходное положение, но не доказывает удобство доступа на любом персонаже. Пакет описывает сопоставление эталона с игровым телом и явные правила преобразования или перепривязки. Body Slots применяет их к наблюдениям фактического тела и калибровки VRIK и движению экипировки. Отсутствующая точка крепления делает слот недоступным, а не незаметно заменяется другой костью. Подгонка игрока хранится отдельно от авторского пакета; удобство доступа всё равно проверяется в игре.

### Определения экземпляры и настройки слотов

Body Slots владеет созданием и реестром определений и экземпляров: постоянными ключами, именованными привязками и локальным размещением, независимой геометрией доступа, видом слота, общими фильтрами допустимого содержимого и сохранением подгонки. Исходные определения и настройки профиля, экземпляры в сохранении и изменения игрока разделены. Повторная регистрация сохраняет подгонку; временные идентификаторы и резервирования создаются заново после загрузки. Создание экземпляра в игре отличается от подготовки его многократно используемого определения.

Фильтры типов, ключевых слов и списков форм поддерживают оружие, щиты, факелы, зелья, еду и инструменты. Зарегистрированные ограниченные проверки уточняют общие правила, не изменяя инвентарь. Body Slots владеет регистрацией политик и версией их настройки; Body Slots использует согласованный снимок правил и вызывает зарегистрированную проверку в объявленной фазе; состояние руки и право на её использование получает от HIGGS. Жизненный цикл колбэка относится к регистрации в реестре; сериализованные определения не содержат исполняемых колбэков. Выбор зелий, запас, свойства оригинала и proxy, сохранение назначений остаются у потребителей. Исключительные или общие привязки определяют право предлагать действие, не превращая реестр в исполнителя инвентаря.

### Слоты надеваемых предметов

Мод экипировки предоставляет записи, ресурсы и набор слотов, подготовленный на эталонной модели. Body Slots создаёт и сохраняет экземпляры и следует их привязкам на фактической модели предмета. Ключ объединяет определение провайдера, конкретный экземпляр экипировки и слот внутри него: одинаковые сумки сохраняют отдельные назначения. Провайдер экипировки проверяет постоянные ключи экземпляров в рамках сохранения и задаёт правила разделения или объединения стопок, клонирования и смены владельца. Повторная привязка восстанавливает один набор; отсутствие предмета, провайдера или установленной идентичности оставляет его недоступным без переназначения другому предмету. Body Slots сохраняет подгонку размещения и визуала; провайдеры содержимого — свои правила по тому же ключу.

### Зоны

Зона — область с привязкой и явно выбранной проверяемой точкой. Для доступа к слоту обычно используется виртуальная кисть VRIK; физическая ладонь HIGGS, контроллер, точка предмета или остриё являются отдельными источниками. Body Slots рассчитывает размещение зоны, проверяет попадание, сообщает вход, выход и наведение. Геометрия наблюдаема независимо от занятости, видимости и резервирования слота; переходы зоны и доступные действия имеют отдельные события. QueryZones обслуживает и подписчиков после входа руки.

Капсула доступа Body Slots — логическая область взаимодействия, отличная от анатомической коллизионной капсулы PPB. Общая математика или необязательная привязка к поверхности не передаёт PPB владение зоной и не делает его обязательным для обычных слотов.

Основные привязки относятся к телу. Привязка к объекту мира могла бы использовать тот же контракт у растения или стены; поиск цели, сбор и пригодность стены остаются у потребителей запросов CommonLib. Потеря привязки делает зону недоступной.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status CreateZone(ClientToken, const ZoneDefinition*, ZoneId* outZone);

Status UpdateZone(ClientToken, ZoneId, const ZoneDefinition*, RequestId* outRequest);

Status DestroyZone(ClientToken, ZoneId, RequestId* outRequest);

Status QueryZones(ClientToken, const ZoneProbe*, ZoneSnapshot* outZones, uint32_t capacity, uint32_t* outCount);
```

### Привязка слотов в игре

Body Slots владеет и определениями, и всей механикой слотов во время игры. Он сопоставляет точки крепления с фактическим телом или моделью экипировки, используя наблюдения VRIK и данные игрового скелета, рассчитывает положение в мире и проверяет доступ руки. Body Slots сообщает доступность привязок, взаимодействие и готовность отображения; геометрия сохраняемых слотов поступает из его реестра. Адаптер позы поставляет данные, но не становится владельцем зон или слотов.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status BindSlotRuntime(ClientToken, const SlotRuntimeBinding*, Lease* outBinding, RequestId* outRequest);

Status CopySlotBinding(ClientToken, SlotId, SlotRuntimeSnapshot* outBinding);

// Events: SlotInstanceAvailable, SlotInstanceUnavailable.

}
```

Body Slots распознаёт перетаскивание слота по согласованному вводу HIGGS и применяет запрос подгонки с ожидаемой версией. Он может временно показывать перемещение, но при отказе возвращает зафиксированное положение. Надевание сумки делает зарегистрированные слоты доступными только после привязки модели; снятие или потеря модели прекращают новые предложения и отменяют незафиксированные операции. Уже переданные предметы сохраняют своё состояние; провайдер содержимого выполняет политику снятия через уполномоченного исполнителя.

### Визуал слотов

Body Slots хранит настройки визуала сумки или держателя и управляет их отображением отдельно от изображения предмета. Привязка указывает, кто рисует сумку — сама экипировка или служба отображения Body Slots, исключая дублирование. Области доступа и хвата задаются явно; габариты модели не становятся зоной активации автоматически. Смена визуала обновляет версии привязок и сообщает готовность или ошибку; готовность изображения предмета указывает версию показанного содержимого. Для этого не требуется передавать новый слот или его визуал в систему кобур VRIK.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status RequestItemPreview(ClientToken, SlotId, const ItemPreview*, RequestId* outRequest);

Status CopySlotPresentation(ClientToken, SlotId, SlotPresentationSnapshot* outPresentation);

// Events: PresentationReady, PresentationFailed.

}
```

### Провайдеры содержимого

Body Slots предоставляет общие фильтры и привязки зарегистрированных провайдеров поведения. Тип содержимого и игровая реакция настраиваются у слота; состояния руки и общие способы её использования берутся из закрытого контракта HIGGS. Слот может принимать только зелья или направлять взаимодействие с едой в стандартизированную службу потребления HIGGS. Готовые обработчики покрывают обычные сумки и кобуры; собственный обработчик задаёт игровой смысл через те же общие операции. BindSlotContent подключает провайдера к слоту Body Slots и ссылается на единую политику реестра. ImportNativeSlotDefinition обозначает необязательный импорт определения штатной кобуры через проверенное сопоставление, а не создание нового слота внутри VRIK. Снятие привязки ждёт завершения её колбэков.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status ImportNativeSlotDefinition(ClientToken, const LegacySlotMapping*, SlotDefinitionId* outDefinition, RequestId* outRequest);

Status BindSlotContent(ClientToken, SlotId, const SlotContentBinding*, Lease* outBinding, RequestId* outRequest);

}
```

Слот может представлять хранимый предмет или выборку из общего инвентаря. Изображение не создаёт дополнительного запаса. Две руки, запрашивающие последний подходящий предмет, резервируют один экземпляр или количество через исполнителя содержимого. Операции указывают физическую руку и все необходимые ресурсы; оригинал, прокси экипировки и отображаемая модель имеют отдельные идентификаторы. Провайдер прокси сохраняет зачарование, заряд, улучшение и владельца.

Провайдер без изменения состояния предлагает доступные действия по неизменяемому контексту. Body Slots связывает предложения с текущей геометрией и передаёт кандидатов HIGGS; окончательное разрешение на использование руки и ввода выдаёт HIGGS. После выбора Body Slots направляет запрос одному назначенному исполнителю. Вход в слот или широковещательное событие нажатия само по себе не даёт подписчикам права выполнять конкурирующие действия. Body Slots публикует зафиксированное содержимое по подтверждению исполнителя с проверкой ожидаемой версии слота; изображение указывает эту версию. Постороннее или устаревшее подтверждение отклоняется. HIGGS координирует физическое удержание и результаты передачи.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status CopyActionOffers(ClientToken, const SlotRequest*, ActionOffer* outOffers, uint32_t capacity, uint32_t* outCount);

// Reserves slot content/access only; hand and input grants belong to HIGGS.
Status ReserveSlot(ClientToken, SlotId, const SlotRequest*, Lease* outReservation);

Status RequestSlotAction(ClientToken, const SlotRequest*, RequestId* outRequest);

Status CopySlotContent(ClientToken, SlotId, SlotContentSnapshot* outContent);

Status UpdateSlotContentFromCommit(ClientToken, SlotId, const SlotContentCommit*, RequestId* outRequest);

// Events: ActionOffersChanged, SlotContentChanged.

}
```

Отказ в доступности до выбора позволяет рассмотреть другое действие. После принятия различаются фиксация, завершение, ошибка и отмена; ошибка после начала операции не превращается автоматически в новое действие на том же нажатии. При пересечении зон Body Slots предлагает кандидатов с явными приоритетами слотов; HIGGS согласует их с остальными действиями руки по правилам пользователя.

### Реестр адаптеры позы и исполнители

API определений и адаптеры наблюдения тела разделены. Body Slots получает положение рук и узлов от доступного адаптера VRIK или другого совместимого поставщика позы; состояния и права рук всегда предоставляет HIGGS. Адаптер не передаёт VRIK владение слотами. Body Slots рассчитывает геометрию, обслуживает переходы, активацию, привязки и отображение. Кадр использует неизменяемую версию настройки; отложенные действия повторно проверяют её, поколения тела и привязок и разрешение HIGGS перед фиксацией.

**Псевдо-ABI**

```cpp
namespace BodySlots {

Status CopyDefinitionChanges(ClientToken, const DefinitionCursor*, SlotDefinitionSnapshot* outRecords, uint32_t capacity, uint32_t* outCount);

Status CopySlotRuntime(ClientToken, SlotId, SlotRuntimeSnapshot* outRuntime);

// Events: DefinitionAvailabilityChanged.

}
```

У каждого состояния один уполномоченный владелец: HIGGS — состояние и использование рук, физические тела кистей; VRIK — поза тела и виртуальных кистей; PPB — анатомические определения, подгонка и смысл касаний; PLANCK — живые физические тела NPC; Body Slots — определения, настройки, геометрия, привязки, взаимодействие и отражение зафиксированного содержимого с его отображением; исполнитель содержимого — игровые назначения и изменение инвентаря. Версии настройки, содержимого и отображения отделены от поколений тела и привязок. Перетаскивание, MCM и изменения через API используют ожидаемые версии; колбэки выполняются в объявленных фазах вне блокировок реестра. Отключение провайдера прекращает новые вызовы и ждёт завершения текущих перед освобождением кода и контекста. Изменения ставятся в очередь на объявленные границы фаз.

## От нажатия до выполненного действия

1. HIGGS сообщает состояние и изменения grip/trigger с идентификатором последовательности ввода. VRIK предоставляет согласованное положение виртуальной руки; PPB — нужные анатомические наблюдения и касания, когда они требуются; Body Slots проверяет зоны и предлагает действия слотов. Состояние и доступность руки сообщает только HIGGS.
2. Моды предлагают действия на основании этих данных. Для удержания или нескольких нажатий распознаватель резервирует ввод с ограниченным сроком.
3. По условиям, привязкам и выбранному пользователем приоритету выбирается одно действие, потребляющее ввод. Наблюдатели могут читать его, но не выполнять конкурирующее действие.
4. Исполнитель повторно проверяет условия и выполняет операцию в допустимый момент обновления игры или физики.
5. Результат различает принятие, фиксацию изменения, завершение, отказ и отмену. В нём указаны запрос, транзакция, провайдер запроса и его поколение, а также выбранный исполнитель. Пересылающий событие провайдер указывается отдельно.

«Запрос принят» не означает «предмет уже передан». Отмена и передача отложенного ввода игре имеют определённые правила. Искусственный игровой запрос не подделывает аппаратное нажатие. Меню, потеря отслеживания, загрузка сохранения и отключение провайдера отменяют ожидающие операции.

## Согласованная физическая работа

PPB предоставляет подогнанную геометрию поверхностей и анатомические данные контакта. Геометрию физической кисти применяет HIGGS, тела NPC — PLANCK; у одного тела нет двух независимых владельцев обновления. Смысл касания не создаёт второго привода или второго подтверждения урона.

У каждого физического тела руки или оружия один окончательный привод HIGGS. Потребители задают поддержанные цели и ограничения через его общий контракт, не регистрируя собственный физический привод. Столкновения, вес и прикрепление застрявшего клинка задают ограничения и цели одного физического решения. Последовательная перезапись положения несколькими колбэками не обеспечивает такую согласованность.

Havok продолжает решать контакты мира, PLANCK — управлять физической анимацией NPC. Мод проникновения управляет раной и правилами извлечения, а PLANCK подтверждает актуальность точки прикрепления к NPC.

Тяжёлый клинок, застрявший в NPC и касающийся стены, проверяет общую модель. Она должна сообщить достижение ограничения, разрыв или отказ и дать владельцу правил обработать результат. Решения об уроне и парировании используют подтверждённые физические данные и проходят определённую обработку попадания.

При лазании точка опоры принадлежит действию мода лазания и занимает указанную руку. HIGGS выполняет стандартный захват опоры, управляет физическим хватом и отключает несовместимые новые действия в заявленной области; VRIK строит согласованную видимую позу. Мод лазания перемещает персонажа через собственный контроллер движения. Для двух рук резервирование проверяется совместно: чужой предмет во второй руке не выбрасывается ради удобства нового действия. Лазание начинается после подтверждения всех обязательных ресурсов: резервирования руки, физической опоры и ограничений. Принятого, но ещё не применённого запроса недостаточно. При отказе подготовки предварительные ресурсы освобождаются до начала движения. Переход к другому действию ждёт подтверждения физического освобождения руки.

## Body Pouches с общими службами

[Body Pouches 0.2.0](https://www.nexusmods.com/skyrimspecialedition/mods/194796) уже использует слоты тела VRIK и захват с употреблением через HIGGS. По умолчанию это один отдельный карман для зелий; совместные и множественные слоты проверены меньше. Карман сохраняет правило выбора зелья и берёт предметы из инвентаря игрока. Изображение бутылки показывает следующий предмет, не создавая отдельный запас. [Код релиза](https://github.com/Vhodnoylogin/body-pouches/tree/0.2.0) показывает, какие части интеграции можно было бы упростить общим контрактом:

| Что сейчас делает Body Pouches | Что могли бы предоставить общие службы |
|---|---|
| Требует разрешённого класса оружия для обнаружения; приостанавливает обычную кобуру для отдельных карманов в режиме exclusive | Определения Body Slots с независимой геометрией и правилами приёма зелий; привязку и права провайдера в Body Slots |
| Читает исходные нажатия контроллера для обхода ограничений совместного слота и повторяет распознавание извлечения | Последовательности ввода и приоритет HIGGS, пространственные предложения Body Slots даже для пустых слотов без оружия |
| Восстанавливает кости и преобразования слотов, соответствие рук и смещение камеры для совместной зоны и диагностики | Снимки зон и проверяемых точек Body Slots, поза тела и кистей VRIK, единое состояние руки HIGGS с указанными координатами и фазой |
| Откладывает отпускание до завершённого обновления VRIK/HIGGS, различает события локальными номерами и отменяет их при захвате или загрузке | Связанное наблюдение отпускания, соответствующий отсчёт зоны и общие правила потери актуальности |
| Извлекает один предмет из инвентаря, просит захват и сопоставляет общий колбэк захвата с локальным сроком ожидания | Один запрос передачи с раздельным результатом инвентаря и хвата, идентичностью предмета и его судьбой при отказе |
| Меняет модель через эффект заклинания, ждёт удаления прежней и показывает один отдельный карман | Независимые визуалы и изображения содержимого каждого слота Body Slots с готовностью, версиями и точками крепления |
| Согласует собственные поколения мира и проверки готовности с сохранёнными назначениями | События жизненного цикла провайдеров и постоянные ключи слотов, при сохранении сериализации назначений в Body Pouches |

Body Pouches продолжит выбирать эффекты зелий, отвергать яды, определять порядок подходящих бутылок и сохранять назначения игрока. Все карманы по-прежнему пользуются одним инвентарём. Поддерживаемый исполнитель инвентаря может использовать проверенные методы извлечения и подбора CommonLib; перенос этих вызовов за службу передачи не переносит правила зелий в VRIK или HIGGS. PLANCK этой механике не нужен и остаётся необязательным до появления функций, взаимодействующих с NPC.

Сохранение назначений остаётся у Body Pouches, но формат записей нужно адаптировать: в релизе назначения связаны с номерами обычных слотов. Миграция с новой версией записи сопоставляет их постоянным ключам обычных кобур, а назначения новых сумок хранит по ключам слотов экипировки, не перенося старое назначение на чужой предмет.

Такая основа могла бы упростить несколько видимых дополнений: независимое отображение карманов в нескольких слотах, явный пользовательский приоритет между зельем и оружием в общем месте, надеваемую сумку для зелий со слотами, следующими за её моделью. Заданная провайдером область доступа у отверстия сумки или горлышка бутылки могла бы сделать извлечение понятнее. Фреймворк показывает проверяемую точку и геометрию для обеих рук; существующая разница между видимой бутылкой и точками активации всё равно требует подгонки и проверок в игре. Наличие нового ABI само по себе не исправляет эту эргономическую проблему.

Более простой мод может поставлять определения слотов, созданные вне игры, регистрировать правила содержимого в Body Slots и исполнителей в службах взаимодействия, задавать изображения Body Slots и реагировать на подтверждённые результаты. Сопоставление запросов и отмена устаревших действий сохраняются, но общая реализация заменяет их частные реконструкции в каждом потребителе. Это предлагаемые изменения, а не дополнительные функции, уже выпущенные в Body Pouches 0.2.0.

## Shields and 2H Weapons Unlocked с общими службами

[Shields and 2H Weapons Unlocked — VR](https://www.nexusmods.com/skyrimspecialedition/mods/184001) автора TheMachinaGod позволяет использовать щиты и двуручное оружие в любой руке. Для нестандартной экипировки мод применяет подменные предметы, или proxy, и собственные плечевые кобуры. В [исходной реализации](https://github.com/SamuelJohnBrown/Weapons-shields-unlocked-skyrim-VR-framework-/blob/7518a1879a78ca494e77cd4d60c76ca5cba77172/main.cpp) они заменяют две плечевые кобуры VRIK, отключая разрешённые в них классы предметов; при наличии FalseEdgeVR это отключение пропускается. Конфликт касается плечевых кобур, а не всех слотов VRIK.

Существующая экспериментальная переделка должна сохранить нестандартную экипировку, но использовать штатные зоны, размещение и отображение VRIK через публичный ABI. Проверенная переделка показывает меч на спине, выдаёт его в правую руку и сохраняет после загрузки. Однако пустая левая рука не получает предложения действия от занятого плечевого слота. Интерфейс также не позволяет явно указать одновременно конкретный слот и целевую физическую руку. Подгонка типа proxy под правила экипировки, кобуры и отображения поэтому требует согласовывать инвентарь, Papyrus, модели и физическое состояние через локальные обходы.

Мод экипировки сохраняет правила нестандартного ношения, выбор proxy и перенос свойств экземпляра. Одна запись об экипировке ещё не доказывает наличие видимой модели, физического тела и рабочей коллизии. Общие результаты позволяют наблюдать эти этапы, но не гарантируют откат после произвольных игровых побочных эффектов. PLANCK участвует в физических попаданиях по NPC и не обязан становиться исполнителем инвентаря или кобур. Это предлагаемые службы, а не законченный перенос или гарантии сегодняшнего ABI.

## Лазание и сбор урожая

[VR Climbing](https://www.nexusmods.com/skyrimspecialedition/mods/170321) самостоятельно организует ограничения HIGGS на время лазания, чтобы хват за стену не сопровождался захватом предмета. Для этого он временно меняет общие настройки HIGGS и затем восстанавливает их. По смыслу это собственная попытка зарезервировать взаимодействие с руками для своей механики.

[Immersive Harvesting](https://www.nexusmods.com/skyrimspecialedition/mods/186754) сталкивается с тем же нажатием grip: возле растения игрок может хотеть собрать его, а не начать лазание. Мод добавляет отдельный обход этого конфликта, вмешиваясь в проверку начала лазания. Получается, что один мод изобретает свой механизм управления взаимодействиями HIGGS, а другой вынужден отдельно налаживать совместимость с этим механизмом.

В предлагаемой синергии эту общую задачу берёт HIGGS. Он знает, какая рука занята, кому принадлежит текущее действие и какие новые действия предложены. VR Climbing запрашивает стандартный захват опоры HIGGS, Immersive Harvesting — согласованное использование руки для сбора. Собственный физический хват лазанию не требуется. HIGGS выбирает допустимое действие по пользовательскому приоритету, подтверждает его начало и сообщает завершение. Каждый мод освобождает только своё резервирование и не восстанавливает настройки поверх чужих запросов.

Например, у растения рядом со стеной пользователь может предпочесть сбор началу лазания. Если рука уже держится за стену, сначала нужно завершить этот хват. Если другая рука удерживает предмет, сбор не должен заставлять её выбросить его. Эти правила обеспечивает общий механизм, доступный всем потребителям HIGGS.

Тогда VR Climbing занимается лазанием, а Immersive Harvesting — сбором и выдачей урожая. Им не приходится заново создавать общий контроль рук и писать отдельный патч друг для друга. VRIK предоставляет положение рук и согласованную видимую позу; PLANCK участвует, когда действие затрагивает физическое взаимодействие с NPC. Движение игрока и правила падения остаются у мода лазания.

## Совместимость и жизненный цикл ABI

Наблюдения PPB подчиняются тем же правилам эпох и инвалидирования, что и остальные провайдеры. Подписка указывает, передаёт ли оперативные контакты или сгруппированные отчёты, и явно сбрасывается при загрузке или замене модели и мира. Отсутствие покрытия PPB не означает пустую или свободную руку. Существующий интерфейс PPB1 сохраняет совместимость и семантику отчётов; снимки с поколениями и удаляемые подписки требуют отдельно объявленного расширения.

Существующие интерфейсы 001 и их поведение сохраняются. Новые службы получают отдельное согласование версии и возможностей. Отсутствующая возможность даёт определённый отказ или документированный старый путь. Старые моды с прямой записью во внутренние данные требуют адаптации для новых гарантий владения.

Новые слоты создаются и обслуживаются Body Slots без обязательного расширения VRIK и без использования реконструированного кода. Публичный 001 VRIK позволяет работать со штатными кобурами, но не превращается в API создания новых слотов. Адаптер наблюдений позы требует проверки доступных игровых узлов, фаз и систем координат на поддерживаемой версии; недостаток данных даёт определённый отказ. Старые кобуры и их API сохраняются. Совместимое сопоставление со штатными четырнадцатью проверяется отдельно: не меняются размер старых массивов, имена Papyrus или сохранённые назначения; настройки импортируются или изменяются только через доступный поддержанный путь. Полный переход выключает соответствующие штатные взаимодействия и отображение до включения аналогов Body Slots. Без проверенного сопоставления и контроля конфликтующего ввода мод не заявляет автоматическую замену. Закрытая модель HIGGS также не означает автоматического контроля старых DLL, которые не участвуют в новом контракте.

Запросы, временные блокировки и подписки принадлежат конкретному клиенту. Один мод снимает только собственный запрос. Для выгрузки прекращаются новые вызовы и завершаются уже выполняемые колбэки. Передаваемые записи содержат размер, единицы, координаты, отображение рук и поколения объектов. Владение выделенной памятью и контейнеры STL через новую границу не передаются.

Псевдо-ABI встроен в разделы соответствующих служб. Описания вспомогательных записей сокращены; числовые значения, компоновка, соглашение вызова и транспорт не утверждены. Полный двоичный ABI потребует отдельного согласования. Общие функции жизненного цикла присутствуют в каждой службе:

**Псевдо-ABI**

```cpp
enum class PhysicalHand : uint32_t { Left, Right };
enum class PoseSource : uint32_t { TrackedController, ResolvedPalm, RenderedIK };
enum class RequestStage : uint32_t {
    Accepted, Committed, Completed, Rejected, Cancelled
};

// Slot definitions/configuration have persistent keys and explicit save/profile scopes.
// Equipment instance keys are durable identities, not pointers or runtime handles.
```

RegisterClient задаёт владельца запросов и ресурсов; ReleaseClient завершает работу этого клиента.

**Псевдо-ABI**

```cpp
Status RegisterClient(const ClientIdentity*, ClientToken*);

Status ReleaseClient(ClientToken);

// Every provider negotiates its own version, table size and capabilities.
```

Ожидающая выполнения операция возвращает идентификатор запроса. Временное воздействие также получает предварительный токен, действующий только после фиксации; при отказе или отмене он освобождается. ReleaseClient и Unsubscribe сначала прекращают новые вызовы, затем подтверждают завершение уже начатых. Отдельный колбэк регистрации снимается по тем же правилам. Код и контекст можно освободить только после подтверждения от всех соответствующих провайдеров. Ожидание не блокирует физический поток или сам колбэк.

**Псевдо-ABI**

```cpp
Status GetRequestResult(ClientToken, RequestId, RequestResult*);

Status CancelRequest(ClientToken, RequestId);

Status ReleaseLease(ClientToken, Lease, RequestId*);

// RequestId is scoped by provider and epoch; TransactionId correlates participants.
```

Записи и массивы копируются в буфер вызывающего; недостаточный размер возвращает требуемую ёмкость. Политики попадания и проверки доступности работают ограниченно и без изменения инвентаря. Фиксируются времена кадра и шага физики отдельно. Загрузка сохранения меняет поколения; временные токены не сериализуются как постоянные идентификаторы слота.

**Псевдо-ABI**

```cpp
Status Subscribe(ClientToken, uint64_t eventMask, EventCallback, void* context, Subscription*);

Status Unsubscribe(ClientToken, Subscription);

Status CopyEventPayload(ClientToken, SnapshotId, void* callerBuffer, uint32_t bufferBytes, uint32_t* requiredBytes);

// Event records name source/forwarder, issuer/epoch, executor, phase and thread.
// Pose/contact records name time, coordinate space, units and generations.
```

Body Slots сохраняет определения слотов и пользовательскую подгонку по постоянным ключам. Временные экземпляры, привязки экипировки, изображения и права на слот после загрузки создаются и проверяются заново; связанные действия ждут готовности. Провайдеры содержимого сохраняют собственное игровое состояние по тем же ключам. Отключение провайдера, недоступность слота и явное удаление сохранённых настроек имеют разные значения и не должны незаметно стирать данные друг друга.

## CommonLib как второй уровень синергии

У синергии два уровня. Первый — согласование поведения HIGGS, VRIK, PLANCK, PPB и службы слотов через их API/ABI: каждый мод предоставляет свои данные и действия. Второй — общая техническая основа в CommonLib: работа с адресами движка и повторяющийся код выносятся из отдельных модов в библиотеку.

Сюда относятся описание и разрешение адресов функций и данных, типизированный доступ к объектам, работа со ссылками и блокировками, преобразования координат, операции со сценой и Havok, лучевые запросы и доступ к контроллеру перемещения персонажа. Вместо собственных адресов и похожих низкоуровневых реализаций моды используют общие методы CommonLib. Исправление такой операции поддерживается в одном месте и становится доступно всем потребителям при переходе на соответствующую версию библиотеки.

Сначала следует использовать возможности текущей сборки CommonLib. Если нужной операции нет, библиотеку можно расширить проверенным методом: установить сигнатуру, структуру данных, адрес для поддерживаемой версии игры и поведение вызова. Общая операция должна быть полезна и участникам синергии, и сторонним модам, а её интерфейс — скрывать детали обращения к движку.

На этой основе HIGGS управляет всеми состояниями и способами использования рук, VRIK — телом и положением виртуальных рук, Body Slots — всей механикой слотов, PLANCK — физикой NPC, PPB — анатомической геометрией и данными касания. CommonLib даёт им общие технические средства, а решения о содержимом сумки, лазании, урожае или попадании принимают владельцы соответствующих механик. Оба уровня дополняют друг друга: общий код работы с движком в библиотеке и согласованное игровое взаимодействие через API/ABI модов.

Для PPB кандидаты на общие технические операции — расстояния до капсул, преобразования координат, проверенный доступ к формам и сцене. Подходящие методы текущей CommonLib следует переиспользовать; отсутствующие безопасные обёртки относятся к предложениям второго этапа. Анатомическая подгонка, смысл касания и право изменять состояние остаются у описанных выше служб. Это обновление не реализует изменений CommonLib.

## Пользовательский приоритет и порядок модов

Пользователь должен управлять тем, какое действие получает преимущество. Например, у растения рядом со стеной один grip может означать сбор, захват предмета или начало лазания. Общая служба должна позволять выбрать приоритет для этого контекста и показывать, какое правило сработало.

Порядок модов может быть одним из способов задать этот выбор. Предлагаемая реализация — отдельные файлы правил совместимости с общим путём: пользователь выбирает победивший файл привычным приоритетом MO2/Vortex. Явная настройка конкретного действия может переопределить порядок, если пользователь её включил. Можно также предложить адаптер, импортирующий выбранный порядок модов в список приоритетов. Для DLL без ESP нельзя обещать, что перестановка ESP или папок сама задаёт порядок их обработки: связь с механизмом выбора нужно реализовать.

Для доступных новых действий предлагается правило: явное пользовательское назначение для контекста, затем выбранный пользовательский список приоритетов, при равенстве — стабильный идентификатор действия. Отсутствие собственного правила использует видимый стандартный профиль. Ни мод, ни время регистрации колбэка не могут незаметно переопределить выбор пользователя.

Предварительное резервирование удержания или нескольких нажатий также выдаётся механизмом выбора по этому приоритету. Оно имеет срок решения и объявленные правила уступки более приоритетному кандидату. Первый зарегистрированный распознаватель не делает остальные действия недоступными по своему усмотрению. Для уже начатой последовательности фиксируется версия правил; изменение настройки применяется к следующей последовательности либо отменяет текущую по явно выбранной пользователем политике.

Приоритет применяется к **допустимым новым действиям**. Занятая рука и уже подтверждённое удержание проверяются раньше выбора: сбор растения не должен вырвать руку из активного лазания. Освобождение или прерывание выполняются явным действием. Подтверждённый перенос предмета нельзя повторить из-за изменения приоритета. Пользователь меняет игровой выбор, а проверки владения, актуальности объектов и однократности передачи сохраняются.
